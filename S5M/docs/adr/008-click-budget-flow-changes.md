# 008 · 点击预算导致的流程与步骤改动

状态
: 通过

日期
: 2026-10-01

决策者
: S5-M 前端（流程裁剪依据 SRS §6.1 与 §6.2，非个人偏好）

## 背景

**UM-NFR-06** 要求「端到端测试覆盖移动（iPhone 与中端 Android 视口）与桌面两种视口的主链路，并校验第 6.1 节的点击预算」，§6.1 又明确「实现必须不超过预算，并以端到端测试校验」。本轮把 §6.1 的 8 条流程接上 Playwright 后，实测有 4 条**结构性超支**——不是渲染慢，而是流程本身多了一步，因此必须改交互而不是改测试：

| 流程 | 预算 | 改动前实测 | 超支原因 |
| --- | --- | --- | --- |
| 审批一个无警告的审批节点 | 2 | 3 | 待办卡片 → 详情页「批准」开面板 → 「确认批准」，中间多一次开面板的点击 |
| 审批一个含警告的审批节点 | 4 | 5 | 「全部接受 → 确认全部接受」之后仍需手动点「批准」才出现确认面板 |
| 运行当前阶段 | 1 | 3 | 项目首页时间线只有「阶段工作区 →」链接，要先展开阶段、再进工作区、再点运行 |
| 上传一份需求材料 | 2 | 3 | 「上传」按钮绑的是空函数 `@click="() => {}"`，真实路径是下方 拍照/相册/文件 三个大按钮 |
| 新建项目 | 4 | 5 | 步骤指示器只画 3 步，实际却有第 4 个「复核」步，多出一次「下一步」 |

## 备选方案

| 候选 | 判定 |
| --- | --- |
| 放宽测试口径（把「打开详情页」不计入点击） | 否决：§6.1 明确「从打开对应入口开始计数（从消息或待办进入计为第 1 次点击）」，改口径等于改需求 |
| 把超支写进文档当已知偏差 | 否决：UM-NFR-06 要求实现不超预算，不是要求测试放行 |
| 按 §6.1/§6.2 的语义改交互 | **取**。每条都对应文档里已有的一句话，不是新发明 |

## 决策

1. **审批面板自动打开（两个预算一起解决）**。待办行的链接改为 `/gates/{id}?approve=1`；`GateView` 在该参数存在、门为 `WAITING_APPROVAL` 且**既无警告也无必须确认项**时直接展开确认面板（§6.1 的 2 步路径）。含警告的 4 步路径则由「确认全部接受」在读者已具备批准条件时接续展开面板——省掉的正是那次纯粹的「打开面板」点击，而 §6.2 的面板确认一步都没少。
   **注意不自动批准**：确认动作仍在面板里，滑动/面板确认分级（§6.2）不因预算而让步。
2. **项目首页时间线内联主按钮**。`ProjectDetailView` 的当前阶段默认展开（`expandedKey` 由 workflow 返回后种入），并在阶段详情里直接放 `FuiActionButton action=stage.run`，于是「运行当前阶段」= 1 次点击。按钮仍受 allowed-actions 与操作人约束（UM-BR-01/02、UM-AC-01）。
3. **「上传」直达系统文件选择器**。`FuiUpload` 暴露 `pickFile()`，页面的「上传」直接调用它；拍照/相册/文件三大按钮保留（UM-REQ-001 要求三来源一键可达），但不再是唯一入口，也就不再是必经的第三步。分级仍预选、仍自动解析。
4. **向导回到 3 步**。删掉第 4 个「复核」卡，把汇总并入最后一步并在其上直接提交（UM-PRJ-001 允许「最后一步显示汇总并提交」），与步骤指示器本来的 3 步一致。

另修 `RunConsoleView` 里滑动确认旁重复的提交按钮（同一动作两个入口，会让「正式提交」的计数含混）。

## 验收对应

- `tests/e2e/clickBudget.spec.ts`：8 条流程 × 4 个视口 project（390 / 393 / 360 / 1280），逐条断言**交互次数 ≤ 预算**并断言流程真的走完（提交发生、页面到达），报告为 `docs/reports/click-budget.md`。
- 计数口径写在 `Counter` 里：`enter`/`tap` 各 1 次，`slide()` 拖动手柄记 1 次（§6.1「滑动确认计为 1 次操作」），并且**不用** `FuiSlideConfirm` 提供的回退按钮——那会把一次手势变成两次点击。

## 后果

正面：§6.1 从「文档里的表」变成 CI 可跑的约束；顺带清掉两个真实缺陷（空的 `@click="() => {}"`、指示器与步骤数不一致）。

负面：确认面板"自己打开"是新的行为，若将来某个门既无警告又需要额外的输入，读者会直接落在面板里而错过被折叠的信息；已用「仅在没有警告与必须确认项时才自动展开」限制范围。

债务：`clickBudget` 依赖 `docs/reports/click-budget.md` 而非 `npm run verify`（e2e 需要构建与 mock，尚未纳入静态检查链）；§6.2 的「输入名称后确认」等更高级别确认可被未来的新页面重新引入超支。

## 复审触发

- §6.1 表格任何一行改动（含新增流程）→ 本 ADR 与测试同时更新；
- 有人为了压预算而删掉一次 §6.2 要求的确认（特别是 PRODUCTION 的滑动确认与输入名称确认）→ 一律回退：预算不得用降低确认强度来换；
- 若产品认为「含警告」的门也应把必须确认项计入「全部接受」→ 本 ADR 第 1 条的范围要重新界定。
