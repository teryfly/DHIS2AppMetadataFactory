# 002 · 依赖图渲染器：自研，SVG 实测达标，Canvas 作默认

状态
: 通过

日期
: 2026-10-01

决策者
: S5-M 前端

## 背景

S5-M SRS **UM-CAP-002**（§4.1，M2）要求图视图：双指缩放、拖动画布与节点、点选高亮邻接关系与引用字段、按对象类型与 businessKey 搜索定位、**节点超过 200 个时默认按类型折叠且可逐组展开**、孤立节点与未解析引用醒目样式、**1,000 个节点在中端手机平移与缩放 ≥ 30 fps**、**5,000 个节点在桌面 ≥ 30 fps**。§4 推荐 AntV G6（按需加载），同时明确「允许自研 SVG / Canvas 实现，须满足 UM-CAP-002」；UM-TECH-003 允许换库但须记录在本仓库的架构决策记录里。**UM-AC-18** 的判据是「打开含 1,000 个节点的依赖图（中端手机）→ 平移与缩放 ≥ 30 fps；超过 200 个节点时默认按类型折叠」。

本轮开始时的自研 SVG（`src/fui/FuiGraphViewer.vue`）没有折叠、没有虚拟化、没有双指缩放、没有节点拖拽、没有邻接高亮，`GraphView.vue` 还硬取 `limit: 400` 并在移动端 `v-if="isDesktop"` 直接不渲染画布——即 UM-AC-18 当时无法执行。

## 备选方案

实测数据在 `docs/reports/graph-bench.json`（`npx playwright test graph.perf` 生成；生产构建 + `vite preview`，CDP `Emulation.setCPUThrottlingRate` 节流 4×，双指经 `Input.dispatchTouchEvent`）。fps 取帧距中位数倒数，60 是 vsync 上限。

| 实现 | 折叠态（默认，UM-AC-18 的口径） | 全部展开（最坏态，超出 AC 要求） |
| --- | --- | --- |
| 自研 SVG（补齐交互后） | 1,000·4×·平移 60 fps（p95 16.8 / 最差 67 ms，91 次重绘）；1,000·4×·捏合 60 fps（p95 16.8 / 最差 33 ms）；5,000·桌面·滚轮 60 fps（p95 16.7 / 最差 17 ms） | 1,000·平移 **30 fps**（p95 83.3 / 最差 133 ms）；1,000·捏合 60 fps 但 **p95 383 / 最差 500 ms**；5,000·桌面·滚轮 **12 fps**（p95 266.7 / 最差 417 ms） |
| 自研 Canvas-2D | 1,000·平移 60 fps（p95 16.8 / 最差 33 ms）；1,000·捏合 60 fps（最差 50 ms）；5,000·桌面·滚轮 60 fps（p95 16.8 / 最差 17 ms） | 1,000·平移 60 fps（p95 116.7 / 最差 217 ms）；1,000·捏合 60 fps（p95 116.7 / 最差 250 ms）；5,000·桌面·滚轮 60 fps（p95 33.3 / 最差 50 ms） |

两臂都在折叠态（默认，即 AC-18 的口径）与「全部展开」最坏态下各测一次：只测折叠态会同时偏袒两种实现，因为 1,000 节点折叠后画面上只有 9 个超节点。

**更正记录（2026-10-01，同一轮内）**：本篇早先的版本声称两臂都测过「全部展开」，那句话当时不成立——`buildScene()` 里 `collapse = count > threshold && expanded.size === 0 ? true : count > threshold` 两个分支求值相同，所以超过阈值的图**永远折叠**，`expandAll()` 与逐组展开都是空操作；旧表的 svg/expanded 行其实测的还是折叠态（当时「节点元素」列恒为 9 就是这个假读数的痕迹）。修法是把折叠状态变成场景数据：按类型判定 `folded`，给被折叠的节点打 `NodeFlag.Grouped`，并导出 `loose`（真正要画的节点索引），两臂与命中网格都只认这三个量。之后 harness 硬断言行的状态与标签一致（`expanded` 行的超节点数必须为 0 且展开节点数 == n，`collapsed` 行反之），报告新增「展开节点 / 超节点 / SVG 元素」三列。上表是修好后重测的数字。

这条更正改变了本篇的结论强度：**SVG 臂在 5,000 节点全展开时只有 12 fps**，Canvas 臂同条件 60 fps。SVG 只作为 `prefers-reduced-motion` / 无 2D 上下文的兜底存在，不再声称它与 Canvas 等价。

| 候选 | 体积 | 判定 |
| --- | --- | --- |
| **自研（SVG + Canvas 两臂）** | 约 6–10 KB，随路由懒加载 | **取**。UM-CAP-002 的阈值（即 AC-18 的折叠态口径）两臂实测达标；Canvas 臂额外在全展开态达标 |
| AntV G6 v5 | 实测 **89,428 B gzip** | 不取：它不省工作（按类型折叠语义、邻接高亮、类型列布局、UM-REV-002 的分组视图仍要自己配），且多一层无法逐帧调的渲染抽象。UM-TECH-003 允许自研 |
| Scalar / Cytoscape / vue-flow | — | 与图能力形态不符或未评估 |

## 决策

保留自研，**不引入任何图可视化库**。同一 `FuiGraphViewer` 组件下实现两个渲染臂，props 契约不变：

- **Canvas-2D 为默认**：状态全在 Vue 响应式之外（`Float32Array` 位置 + `Uint8Array` 标志位 + `Int32Array` CSR 邻接表 + 均匀网格命中索引），视口裁剪、标签裁剪、边按 (edgeKind, 高亮) 分桶一次 `beginPath`、DPR 上限 2、每帧至多一次绘制、手势只写 store 置 dirty。理由是节点拖拽与 5,000 级 DOM 成本在这里是 O(视口)，而在 SVG 里是逐节点属性写。
- **SVG 臂保留**给 `prefers-reduced-motion` 与拿不到 2D 上下文的环境，并作为基准 harness 的 A/B 臂。它在 AC-18 口径（默认折叠态）达标是上面表格测出来的，不是假设的；全展开态不是（5,000 节点 12 fps），所以它不承担默认路径。

**方法论警告（重要）**：第一版 harness 用 CDP 合成触摸把事件投在页面包装器中心，而 AppShell 的冷启动操作人对话框是 Vant 模态、会锁 `body` 并吞掉全部指针事件。那次运行报告了 24 项「60 fps」，实际重绘次数是 **1**。现在每个采样都强制断言重绘次数 > 20 并把数字写进报告的「重绘」列——没有这一列，任何 fps 读数都可能只是空转。任何后续基线对比都必须沿用这个门槛。

同时修掉的既有缺陷：`view` 默认值 `dependency` 不是 S1 合法取值（只接受 `domain|mapping`，且 `mapping` 必须带 `environmentKey`），此前图页对真实 S1 首次加载即 400；`limit` 由 400 提到默认 1,000、可选 5,000；移动端渲染画布；左侧列表改用 `FuiVirtualList`（`FuiList` 是无限滚动不是虚拟列表，UM-REV-006 要求 5,000 条虚拟滚动）；搜索改为复用 S1 的 `matched` 做定位而不重绘模型。

## 验收对应

- UM-AC-18：`tests/e2e/graph.perf.spec.ts`（两臂 × 折叠/展开 × 平移/捏合/滚轮），数字入 `docs/reports/graph-bench.md`
- 折叠与逐组展开：同文件 `over 200 nodes collapse by object type by default`
- UM-TECH-002：`src/test/fuiPurity.test.ts`（图内核只在懒加载目录）

## 后果

正面：UM-CAP-002 的六项交互与两档帧率都有数据；没有新增运行时依赖；首屏体积不变。

负面：自研渲染器意味着折叠语义、命中测试、邻接高亮由本仓库长期维护。60 fps 是 vsync 上限，所以**中位帧率不可区分两臂**，只有尾延迟能：p95 帧距 SVG 16.8–49.9 ms / Canvas 16.7–16.8 ms，最差帧 SVG 33–83 ms / Canvas 17–33 ms。也就是说两臂都过了阈值，但 SVG 在 4× 节流下会出现可见的单帧卡顿，而 Canvas 没有。选 Canvas 为默认的依据是这组尾延迟与拖拽/DOM 规模的可控性，不是中位 fps。

债务：节点拖拽与邻接高亮未在节流手机上单独测帧率（UM-CAP-002 的阈值只写了平移与缩放）；`prefers-reduced-motion` 下的 SVG 臂没有虚拟化，读者若手动全部展开会掉到实测的 12 fps（5,000 节点）——要么给 SVG 臂加视口裁剪，要么在降级臂上禁止全部展开，二者都需要先有数字，现在有了。

## 复审触发

- 阈值口径变化（例如要求「拖拽节点也 ≥ 30 fps」或把「全部展开」纳入验收）→ 必须补测并重判；
- 出现 5,000 节点以上的真实项目 → 需要重新评估折叠阈值与列布局；
- 有人提出引入 G6 以省去维护 → 须先量化它能省掉哪一部分本 ADR 列出的自研工作。
