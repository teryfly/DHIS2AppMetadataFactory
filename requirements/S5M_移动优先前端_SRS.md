## 1. 目的与范围

### 1.1 目的

S5-M 的目标是一套**不依赖 `@dhis2/ui`**、以中文用户使用习惯设计、**移动端优先并兼容桌面端**的前端。它让实施人员、审批人和项目负责人在手机上就能完成日常的大部分工作——查看进度、回答问题、审批、发起运行与提交；需要大量编辑的工作（JSON 编辑、复杂图审核、完整 Diff）在桌面端完成。

### 1.2 设计目标

| 目标 | 含义 |
| --- | --- |
| 符合中文使用习惯 | 底部标签导航、待办中心、红点角标、下拉刷新与上拉加载、底部弹出操作面板、审批流与物流式进度时间线、中文术语与中文错误说明 |
| 人性化 | 每个页面都告诉用户“现在是什么状态、下一步该做什么”；空状态给出引导；错误给出原因与解决办法；可撤销的操作不打断确认，不可逆的操作才二次确认 |
| 减少点击 | 为关键任务设定点击预算（第 6.1 节）；首选动作始终在拇指可达的底部；智能默认值；一次加载完成审阅所需的全部信息 |
| 移动优先 | 以 360 px 宽为基准设计；单手可操作；弱网可用；支持微信、企业微信、钉钉内置浏览器 |
| 兼容桌面 | 宽屏自动切换为侧栏 + 列表 + 详情的多栏布局，并开放编辑类重功能 |

### 1.3 范围内

与 S5 SRS 相同的全部功能（对照见附录 A），以本文的交互与技术要求重新实现：应用框架、操作者标识、工作台与待办、项目与向导、阶段工作区、输入与需求、问题、人工编写、审批、审核视图、部署、变更请求、审计、通知、环境、治理与设置、实时更新。

### 1.4 范围外

| 不负责 | 说明 |
| --- | --- |
| 任何业务判定 | 动作是否合法由 S1 的 `allowed-actions` 决定（总体 SRS FR-IF-003） |
| 调用 S1 以外的任何服务 | 只调用 S1 公共 REST API 与 SSE（UI-IF-001） |
| 直接改动后端 | 不在本子系统内改 S1；需要的能力由 S5-M 按第 12 章提出、S1 落地并递增契约版本。所有读写仍只走 S1 公共 REST 与 SSE |
| 原生 App、小程序 | 只交付 H5 / PWA；在微信、企业微信、钉钉中以网页方式打开 |
| 系统级推送 | 不做 Web Push（需要后端支持）；消息触达依靠站内通知与 S1 已有的邮件、Webhook 渠道（Webhook 可接入企业微信或钉钉机器人） |
| 浏览器内 Mock 层 | 不引入 MSW / Service Worker 拦截式的浏览器 Mock。开发与 e2e 使用独立的 Node 替身 `scripts/mock-s1.mjs`，它只覆盖用例需要的端点与 SSE，**不是完整契约**，界面自身不携带演示数据 |

登录与权限界面，以及项目成员、受限产物授权、生产豁免的页面**不属于范围外，本期全部交付**：登录页、OIDC 回调、账号、角色与项目级授予均已上线；成员、受限产物授权、生产豁免三页在移动端以 `/projects/:id/members`、`/grants`、`/exemptions` 存在，入口在项目详情，`src/test/m4Presence.test.ts` 与 `tests/e2e/m4Presence.spec.ts` 断言它们必须存在。

**问卷上的标记不是枚举记号**：`recommended=true` 读「推荐」、`changesUid=true` 读「会改变 UID」、
`regenerates` 非空读「需重新生成 n 个产物」、`blocking` 读「阻断／选填」。它们与 `answerMode` 一样
来自 `questions.recommended` / `questions.changesUid` / `questions.regenerates` /
`questions.singleHint` / `questions.multipleHint`（`zh-CN.ts` 与 `en.ts` 成对），**不进** `labels.ts`
的记号表；两种语言的缺词由 `src/i18n/parity.test.ts` 判红。`answerMode` 不是 `MULTIPLE` 的取值
（含未知值）按单选渲染，界面不把该记号本身印出来。

**两处一个记号两句话**：① `ACTIVE` 既是"这个环境没被停用"，也是"这个项目还在做事"，界面把它分成两块——
环境/账号读 `stageStatus.ACTIVE`（启用中），项目走 `workflowStatusLabel()` 取"进行中"那个词；② 预算的
`WARNING` 与问题的 `WARNING` 不同义，所以预算单独一张（`budgetState`），不共用 `severity`。

**故意不进词汇表的四类**：① 审计事件类型（`cp.stage.started` 这一串约 40 个）——审计页是给安全审计员核对
链路的，**原样抄写服务端记号才是正确的**，翻译它等于制造一个对不上的引用；② DHIS2 对象类型
（`organisationUnit`、`programRule`）与 HTTP 方法——那是 DHIS2 与 OpenAPI 自己的词汇，不是本产品的；
③ 业务键、UID、哈希、模型名、端点地址——数据，不是状态；④ **服务端自己写的句子**——通知的 `message`
是 S1 落库的原文（`REQUIREMENT_GATE is waiting for approval`），界面对它只做两件事：把自己那一行标题
换成词（`notifications.types.*`，键名与记号同拼法），原文留在下面一行。改抄写来的句子等于让界面替服务端
说话，而排查时需要的正是那句原话。登记表的 `role`、连接的检查名
（`addressReachable`）、IAM 动作串（`gate.approve`）同属"能与服务端逐字对照"的标识，保持原样。

## 3. 设计原则

- **UM-P-01 状态以服务端为准**【直引】（UI-BR-01、UI-BR-02）所有业务状态来自 S1；按钮可用性只由 `allowed-actions` 决定；本地只保存界面状态、操作人姓名（未启用认证时）、语言与表单草稿。已缓存的读取结果属于上一个身份这一点同样算状态：身份一变，缓存即失效（UM-NET-007）。
- **UM-P-02 一屏一件事**【新增】每个移动端页面只有一个主要目的与一个主操作；主操作固定在底部操作栏，次要操作收进“更多”面板。理由：减少选择负担与误触。
- **UM-P-03 先结论后细节**【新增】详情页顶部先给结论卡片（状态、影响、下一步），细节折叠在下方。理由：移动端阅读成本高，用户多数情况下只需要结论。
- **UM-P-04 可撤销不确认，不可逆才确认**【新增】对可撤销或无副作用的操作直接执行并提供撤销；对不可逆操作（正式提交、删除、归档、清除内容、提交整页问卷、批准审批）使用与风险相称的确认方式（第 6.2 节）。理由：既减少点击，又守住高风险动作。
- **UM-P-05 不让用户记忆**【新增】记住上次的项目、筛选条件、数据分级选择、列表位置；返回时回到原来的滚动位置。
- **UM-P-06 移动端不做重编辑**【新增】JSON 编辑、图的自由布局、完整 Diff 在移动端提供只读或精简视图，并提示“在电脑上继续”，可一键复制当前页面链接。

### 4.1 重型能力验收标准（UM-CAP）

- **UM-CAP-001 JSON 编辑器（桌面端）**：语法高亮；按 S2 分节 Schema 实时校验，错误定位到行列与字段路径并在编辑器内标注；基于 Schema 的键名与枚举值补全；格式化；与表单双向同步且不丢失未知字段；5,000 行文档编辑时输入延迟 < 100 ms。普通 textarea 不满足本条。
- **UM-CAP-002 图视图**：双指缩放、拖动画布与节点、点选节点高亮其邻接关系与引用字段；按对象类型与 businessKey 搜索并定位；节点超过 200 个时默认按类型折叠、可逐组展开；孤立节点（`orphans`）与引用断点（`unresolvedRegistryRefs`）在图上以醒目样式标出——它们只是图上的标注，**不得**作为第二份“问题列表”与校验问题并列展示，问题处理一律以校验问题（S1 CP-UI-004）为准，图上的断点可提供“查看相关校验问题”的跳转；1,000 个节点的图在中端手机上平移与缩放 ≥ 30 fps，5,000 个节点在桌面端 ≥ 30 fps。
- **UM-CAP-003 OpenAPI 查看（桌面断点，本期交付）**：按标签与 operationKey 浏览；展开任意层级的嵌套 Schema 并解析 `$ref`；显示请求与响应示例、参数、错误响应、`x-registry-refs`；全文搜索。**只读**，见 UM-REV-005。
- **UM-CAP-004 只读内容查看器**：JSON 与 YAML 的折叠树视图、行号、搜索与复制；大文件分段加载。

### 5.2 操作人与偏好（UM-ME）

- **UM-ME-001**【调整】（UI-OP-001～004）未启用认证时首次使用要求填写操作人姓名，保存在本地，所有改变状态的请求自动附带 `X-Operator`；未填写时全部改变状态的操作不可用，并在底部提示“先填写姓名”（一次点击即可跳转到填写处）。启用认证（`authMode != off`）后身份来自会话：不再弹出填写姓名的引导，也不得因未填写姓名而禁用动作，“我的”页面显示当前账号而不是一个填了也不生效的姓名框。
- **UM-ME-002**【新增】“我的”页面提供：界面语言（简体中文默认，英文可选）、字号（跟随系统 / 标准 / 大 / 超大，大字号下布局不溢出）、深色模式（跟随系统 / 开 / 关）、清除本地缓存。理由：适老化与夜间使用。
- **UM-ME-003**【新增】（CP-IAM-002、UM-NET-009）**本地账号与组织单点登录并存**。`authMode` 为 `oidc` / `both` 时，`/login` 在账号口令表单之外给出“使用组织账号登录”：按 `GET /api/v1/auth/oidc/request?redirectUri=…` 返回的 `authorizationEndpoint`、`clientId`、`responseType`、`scope`、`state`、`nonce` 组装跳转；浏览器回到 `/auth/callback` 后，`POST /api/v1/auth/oidc/exchange` **只兑换一次**（`code` 是一次性凭证，重挂载不得再发），`state` 由服务端与它签发的 HttpOnly cookie 比对。组织侧带回的 `error` 是对方的拒绝，原样说明；兑换失败显示服务端错误码对应的中文。成功后回到登录前那一屏（`returnTo` 只接受站内路径）。界面不保存 token、code 或 state 到任何浏览器存储；`authMode=off` 时不显示任何登录入口。

### 5.3 请求、错误与实时更新（UM-NET）

- **UM-NET-001**【直引】（UI-REQ-001～004）创建类与执行类动作生成幂等键，同一动作的重试复用该键；409 时刷新资源与 `allowed-actions` 后说明原因；`APPROVAL_INVALIDATED` 时提示“内容已变化，请重新查看”并刷新；正式提交的网络失败显示“结果待确认”，不自动重提。
- **UM-NET-002**【调整】（UI-REQ-002）错误提示使用中文口语化表述，结构为“发生了什么 + 怎么办”，例如“当前不在允许提交的时间段（每周二、四 20:00–23:00），请在时间段内再提交”；`details` 中的信息（时间窗、缺失权限、冲突字段等）直接显示在提示中；提供“复制排查编号”（correlationId）一键复制。
- **UM-NET-003**【直引】（UI-RT-001～005）通过 SSE 实时刷新，断线后携带最后序号重连补发，收到 `stream.reset` 时全量刷新，显示 Agent 与执行进度。
- **UM-NET-004**【新增】在 SSE 不可用或频繁断开的环境（部分内置浏览器、弱网）中，自动降级为轮询当前页面相关资源：前台每 5 秒一次，页面切到后台时暂停，回到前台立即刷新一次；网络恢复后优先回到 SSE。轮询只是刷新手段，状态仍以 REST 结果为准。理由：微信等内置浏览器对长连接支持不稳定。
- **UM-NET-005**【新增】弱网与离线：离线时顶部显示黄色提示条，页面保留最近一次加载的内容并标注“离线，显示的是 xx:xx 的数据”；离线期间所有改变状态的操作不可用。PWA 只离线缓存静态资源，不缓存业务接口结果到持久存储。
- **UM-NET-006**【新增】所有操作在 100 ms 内给出视觉反馈（按钮进入加载态或骨架屏）；列表与详情使用骨架屏而不是整页转圈。
- **UM-NET-007**【新增】（UM-P-01、FR-SEC-005）会话变化就是身份变化，缓存的服务端状态属于上一个身份：登录成功后必须让全部服务端状态失效并重新拉取，不得要求使用者手动刷新才看到自己的数据，同时清除登录前因无会话而产生的“未认证”提示；退出登录时丢弃上一个账号的数据但不重发请求（没有会话时的重发只会换来一排 401）。
- **UM-NET-009**【新增】（CP-IAM-004、CP-IAM-005、FR-SEC-005、UM-NET-002）会话在使用中途到期必须**可见且可自助恢复**：任一读取或写入回答 401 `UNAUTHENTICATED` 时，界面把会话收为“未登录”并**把操作者带到登录页 `/login`**，页面上说明"为什么会到这里"（会话已过点，不是崩了），同时**只提示一次**——一个过点的会话是一个事件，逐屏弹错误会把一件事说成二十件。登录页**替代**了此前"在当前屏幕上开一个登录弹窗"的做法：弹窗会把操作员正在看的那一屏压在模态下面，而它引用的那些读数此刻全都回答失败。原先的 `?next=` 语义保留：登录后回到原来那一屏（只接受站内路径，且这一跳用 `replace`，不让操作员能回退到一个已经进不去的屏幕）。收为未登录时**必须保留服务端报告的 `authMode`**：把它一并清空会得到 `off`，而那正是唯一一种不显示登录入口的形态（UM-ME-001），症状是“界面既不让登录也不让操作”。缓存按 UM-NET-007 的退出路径处理：丢弃但不重发。
  同一处必须提供**修改自己的口令**：`POST /api/v1/users/{user_id}/password`（`user_id` 是当前账号自己的 id） 不需要 `user.manage`（CP-IAM-005），而 S1 在写入口令时吊销该账号全部会话（CP-IAM-004），因此界面必须在按下去之前说明“改完要重新登录”，并在成功后明确落到登录态，而不是留下一个说不清的 401。口令输入格 `type="password"`、改完即清、不进任何浏览器存储；被标记 `mustChangePassword` 的账号额外显示原因。该标记是报告位、服务端不拦调用，因此界面不得假装它已经把人挡住。
- **UM-NET-008**【新增】（CP-API-002、UI-OP-005）`X-Operator` 的取值超出 ISO-8859-1 时先 `encodeURIComponent` 再发送。理由：header 值被 Fetch 标准限制在 Latin-1，中文姓名在移动浏览器里同样是发出前就被拒绝，症状是每一次写操作都提示「无法连接服务器，请检查网络」——而这一产品的主要操作者姓名就是中文。Latin-1 装得下的姓名按原样发送；S1 1.6.0 起两侧都能还原成同一个名字（`rest/middleware.py:decode_operator`）。
- **UM-NET-010**【新增】（CP-UI-022、S5IF-BP04）**`NOT_GENERATED` 是状态，不是故障**。蓝图草稿与分节条目读到 `404` 且 `details.reason = NOT_GENERATED` 时，查询层把它解析为 `null`（“这一阶段还没跑过，所以还没有内容”），输入页与人工编写按空内容渲染，不弹错误；`NOT_EXIST`、以及没有 `reason` 的非派生资源仍按错误上报，不吞。派生资源（依赖图、登记表、校验问题、OpenAPI／UI 规格、交付包）在 `NOT_FOUND` 且没有 `reason` 时按产出阶段进入 UM-REV-007 的引导空状态，并**不再叠加**一条“请求的对象不存在”的 toast——同一件事只说一次。

### 5.6 阶段工作区（UM-STG）

- **UM-STG-001**【调整】（UI-WB-001～003）阶段页顶部为结论卡片：阶段状态（中文，含颜色与图标）、依据的蓝图版本或草稿、输入完成度（进度环，点击展开缺失项）、待确认问题数、阻断问题数、最近运行时间；下方依次为：待处理事项（问题、反馈、阻断原因）、产物、审核内容。
- **UM-STG-002**【直引】（UI-WB-006）底部操作栏的主按钮由 `allowed-actions` 决定，按“运行 → 提交审批 → 去审批 → 重跑”的优先级选出当前唯一的主操作；其他可用动作放入“更多”面板；不可用的动作显示原因。
- **UM-STG-003**【直引】（UI-WB-007～009）被驳回时置顶显示驳回理由；失败或阻断时显示来源阶段并一键跳转；待人工核实时提供“查看对账结果”与“标记结果”；策略拒绝或预算超限时说明原因并引导“改为人工编写”。
- **UM-STG-004**【新增】运行中的阶段显示进度条与当前步骤（来自进度事件）；用户离开页面后，任务完成时通过站内通知与待办角标提示，无需停留等待。
- **UM-STG-005**【新增】（CP-UI-004、UM-BR-01）**取消一次 Agent 运行，而不是取消整个工作流**。运行卡片在 SSE 进度帧带 `agentRunId`（进度 store 里保存的 run 地址）且 `allowed-actions` 给出 `agent.cancel` 时显示危险色「取消 Agent 运行」；按下先确认，随后 `POST /api/v1/workflows/{workflowId}/agent-runs/{runId}/cancel`。缺 run id 的帧不抹掉先到的 id，也不显示一个无法定址的按钮；S1 说不可取消时不出现该按钮，界面不读状态徽章猜。取消成功后清掉这一阶段的本地进度，阶段状态以随后的 REST/SSE 结果为准。

### 5.7 输入与需求（UM-REQ）

- **UM-REQ-001**【调整】（UI-REQS-001）上传支持拍照、相册与文件三种来源；数据分级默认取本项目上次使用的分级（首次为“内部”），**个人健康或身份信息（PHI/PII）永不作为默认值**，选择时需要再次确认；上传前按 S1 设置检查类型与大小；上传完成后自动开始解析，无需再点“解析”。
- **UM-REQ-002**【直引】（UI-REQS-002、003）逐项显示解析状态与错误；表格清单的列映射复核以“源列 → 目标字段”的卡片逐列展示，建议映射已预填，确认无误只需点一次“确认映射并重新解析”。
- **UM-REQ-003**【直引】（UI-REQS-004）需求页分两块：按类别分组的规范化需求（每条显示来源与置信度，点来源跳到原文位置），以及草稿或已批准版本中的需求条目。
- **UM-REQ-004**【新增】（UI-REQS-003、S5IF-BP02）**需求条目手写页** `/projects/:id/requirements`：把蓝图草稿的 `requirements` 段当作唯一清单，解析产出的条目与手写条目同列，不是第二份数据。顶部在「草稿／已批准」之间切换——需求阶段已通过时默认打开「已批准」并只读，避免打开一个空草稿；「草稿」可按 `CANDIDATE` / `CONFIRMED` / `REJECTED` 筛选并显示条数。每条显示 `businessKey`、优先级、置信度、来源（解析材料／决策／手写）、待确认问题数与理由。提供新增、编辑、删除、单条通过／驳回，以及「全部待定通过」；删除与全部通过先确认。阶段页在需求阶段给出进入本页的入口。
- **UM-REQ-005**【新增】（S5IF-BP02、CP-UI-022）**写入协议与字段上限**。新增只发一个 `add /requirements/items/-`（追加，不覆盖别人这期间加的条目）；编辑与删除**先重读** `GET /api/v1/projects/{id}/blueprint/entries?sections=requirements&source=…`，再以 `replace /requirements/items` 整段替换，`baseVersion` 取刚读到的版本。不得按下标寻址，也不发 `test` 哨兵：读模型按 `businessKey` 排序而补丁引擎只认数组下标，界面读不到条目在存储数组里的位置（实测会把一次正常删除挡成 422）。表单上限读 `GET /api/v1/projects/{id}/blueprint/section-schemas/{section}`（`section=requirements`）：`businessKey` 的模式与长度、`statement`／来源说明长度、`priority`／`status`／`openQuestions.severity` 枚举、`confidence` 区间；本机常量只在 Schema 未到时兜底。`businessKey` 是身份，编辑态锁死；改一条时与读到的原条目合并，保留 `actors`、`source.artifactId` 与表单未展示的字段。阶段关闭（`allowed-actions` 不再给 `patch.submit`）时收起全部写入口，说明当前阶段状态并给出变更申请入口；`SCHEMA_ERROR` 提示重读后重试，不静默覆盖。

### 5.8 待确认问题（UM-Q）

- **UM-Q-001**【调整】（UI-Q-001、002）问题卡片显示：问题、影响对象、严重程度、阻断／选填、题型；每一条建议给出文本、理由（`rationale`）、是否推荐（`recommended`）、是否改变 UID（`changesUid`）与需重新生成几个产物（`regenerates`）。建议之外始终有「其他（自行填写）」，选中后展开文本输入；单选选「其他」时只提交 `customText`，多选时「其他」的文本可与所选建议一起提交。
- **UM-Q-002**【调整】（UI-Q-003、S1 CP-Q-005）**整页问卷，一次提交**。以当前问题的阶段为范围，取 `GET /api/v1/workflows/{workflowId}/questions` 中同一 `stageId` 且 `status=OPEN` 的全部问题，按 `HIGH` 优先、同级按文本排序，同屏逐题作答；页头显示「已答 n/m 题」，并说明提交后会基于原上下文重新生成。`answerMode=SINGLE` 渲染单选，`MULTIPLE` 渲染复选；`recommended` 的建议带「推荐」标记，「其他」展开自由文本。底部只有一个「提交全部回答并重新生成」，提交体是 `POST /api/v1/questions/answers` 的 `answers[]`（每题 `questionId` + `suggestionIds[]` + 可选 `customText`，空答不发送；契约上限 200 题）。**提交后不可撤销**：逐题回答的 5 秒撤销条已随整页问卷撤下（UM-BR-08）。
- **UM-Q-003**【调整】（S1 CP-Q-005/007）**服务端 resume 一次，下一轮原地显示**。响应 `QuestionnaireAnswerView` 带 `resumed`、`status`、`answers[]` 与 `questions[]`；`questions` 非空即下一轮问卷，页面以服务端返回的列表原地替换当前问卷并滚到顶部（旧题不再显示），提示「已提交。模型根据回答生成了 n 个新问题」；为空则提示「已全部回答，系统将继续运行」并回到阶段页（无阶段则回待办）。页面不自行猜测是否产生新问题，也不再逐题调用回答接口；未点提交就离开页面不发任何回答，草稿不跨页保留。
- **UM-Q-004**【新增】（UM-Q-002、UM-BR-08）**阻断校验与计数**。任一 `blocking` 问题没有有效答案（单选未选、多选为空、选「其他」但文本为空）时提交按钮按住；页头与底部各给一次「还有 n 个阻断问题未回答」，每题下给「这是阻断问题，必须作答」。非阻断题可留空；已答计数只统计有有效答案的题。按钮是否可用仍先问 `allowed-actions` 的 `question.answer`；本地校验只决定“填完了没有”，不决定“能不能写”。

### 5.10 审批（UM-GATE）

- **UM-GATE-001**【调整】（UI-GATE-001）审批页首屏是**结论卡片**：这次批准会发生什么、影响哪个环境、产出什么（一句话）；下方依次是：发现了什么、为什么（决策与理由）、还有什么不确定、可以改变什么，全部可折叠。页面采用接近钉钉审批的版式，审批人姓名、时间、意见以时间线呈现。。页头要写出这一节点关掉哪一段活（「审批 · 需求整理」，与桌面 `GatePage` 的页头同一句话——只有状态和「批准后会发生什么」的一屏，读的人不知道自己在批哪一段）；批准记录那一张的标题是「审批进度」，不是复用页名。六问的答案一律读成**行**：`why` 里一条决策一行（选了什么 — 为什么），`canChange` 里一条动作一行（`action: … · target: … · invalidatesGate: …`，动作名保持服务端拼法，它同时是权限名）；**结构体不得以 JSON 形式印在屏幕上**——括号、引号与 `null` 等于让审批人自己解析返回值。没有决策可讲时给一句现成的话，不给空 {}。守卫在 `S5M/tests/e2e/gateExplanation.spec.ts`（4 条 × 视口）

- **UM-GATE-004**【新增】批准与驳回都在底部弹出面板中完成：面板显示将要执行的结果摘要与可选意见，点“确认批准”或“确认驳回”提交，无需跳转页面；成功后自动返回待办并定位到下一项。

- **UM-ADM-003**【直引】（UI-ADM-004）系统设置。
- **UM-ADM-004**【新增】（UI-ADM-002、S5IF-SEC01）一次性凭证录入：口令类输入 `type="password"`、`autocomplete="new-password"` 以避开浏览器已存的自动填充，Basic 认证的用户名与口令按 `user:password` 组合成一个值，提交 `PUT /api/v1/secrets/{name}` 后把响应给出的 `db://name` 回填进引用字段。值不写入任何浏览器存储、不进 URL、请求返回后（成功或失败）立即从组件状态清除；界面永不显示已存值的原文、掩码或长度（S5IF-G09）。旁边提供"选择已录入的引用"下拉（数据来自 `GET /api/v1/secrets`，只列名字与时间）。可用性只来自 `allowed-actions` 的 `secret.manage`；`GET /api/v1/setup` 报告 `credentials.storeAvailable = false`（主密钥未配置）时录入端点回 503，此时提示改用 `env://` 引用，而不是弹一句"保存失败"。
- **UM-ADM-005**【新增】（S5IF-GOV20）**提供方测试连接**：治理页每个提供方行一个「测试连接」，调用 `POST /api/v1/governance/providers/{name}/test-connection`，结果就地显示在那一行——`healthy` 为真读「地址应答正常」，否则读「地址没有给出可用应答」，并把 `detail`（如 `provider answered HTTP 401`、`model endpoint unreachable: ConnectError`）原样附在后面；请求本身失败读「这次探测没完成，稍后重试」。探测不写列表缓存、不失效列表，每次点击都新发；按钮可用性来自 `governance.provider.enable`（与启停、编辑同一个动作），不另设权限。

### 5.15 装机引导（UM-SET）

手机上装完一套 Factory 后，第一个障碍不是操作而是**看不出还缺什么**：环境、模型提供方、项目分属四个入口，且环境入口不在底部五个标签里。本节与 S5 的 UI-SET 同源同事实，只改变呈现方式（UM-UX-003 要求空状态给出下一步，本节把"下一步"从单页扩展成一条路径）。

- **UM-SET-001**【调整】（S5IF-SET01、UM-BR-01）提供"开始使用"页，清单为**四步**：`模型与提供方 → DHIS2 环境 → 第一个项目 → 跑阶段、审批、正式提交`，并为**一步一屏**：顶部一条可横滑的步骤条（当前一步标 `aria-current="step"`），下面一次只展开当前这一步，屏内直接给完成它所需的表单。模型与环境两步打开与治理页／环境页**同一份** `ProviderSheet` / `ModelSheet` / `EnvironmentFormSheet`，不另养一套登记规则；项目与流水线两步跳到页面（不为“留在本页”伪造历史）。每项状态只来自 `GET /api/v1/setup` 的事实与 `allowed-actions`，缺失条目按"不可用"处理，绝不臆测（UM-BR-02）；点步骤条换步不离开本页。被 S1 withhold 的分组显示"无权查看"，不计为待办。
- **UM-SET-002**【调整】（S5IF-SET01、UM-NET-002）`configuration.problems` 非空时在页顶原样列出（中文说明 + 可复制原文），并说明句子指向 `env` 文件的变量名、不含取值；`identity.pendingPasswordChange` 为真时提示先去改口令。**`providers` 不是一步**：`GET /api/v1/setup` 的 `providers` 在清单末尾以「能力接入」事实卡显示，`real` / `fake` 由前端一处标签映射成「真实接入」／「演示替身」；任一子系统为替身时明确标注"结果不可交付"。该卡不提供任何表单——`provider_mode` 是部署配置，浏览器里没有任何控件能改变它，给一个能填的表单就是骗人。
- **UM-SET-003**【调整】（UM-ADM-001、UM-ADM-004、S5IF-ENV08、S5IF-SEC01）环境登记后未通过连接测试（`environments.neverTested`）不得显示为已完成；清单该项为"待测试"。这一步就地打开环境表单：接口地址、类别、认证方式与各凭证范围，凭证一栏用一次性录入控件填用户名/口令或 API key（UM-ADM-004），也保留手填 `env://…` 的路径；保存后仍在本页给出结果，不再要求换页。环境列表页在无数据时必须给出创建入口与说明，而不是一张空表。
- **UM-SET-004**【调整】（UM-PRJ-001、UM-BR-01）新建项目的入口（首页、项目列表、向导末页）其可用性一律来自平台作用域 `allowed-actions` 的 `project.create`；向导在环境清单为空时给出原因与去登记环境的跳转，不允许出现"下一步按不动且无提示"。项目向导与工作台是页面而不是底部面板，因此这一步保留跳转。
- **UM-SET-005**【调整】（UM-ADM-002、S5IF-GOV05、S5IF-GOV06、S5IF-GOV07）引导清单是**四步**：模型与提供方第一、环境第二、项目第三、跑通流水线第四；前两步在本页打开登记表单，后两步跳到项目页。「能力接入」降为清单末尾的一张事实卡（`FACTORY_PROVIDER_MODE` 在服务器的 env 文件里，手机上没有任何控件改得动它）。已登记的模型同样要能改，规则与 S5 的 UI-SET-005a 一致：表单收「已存行或空」，非空是编辑且**只发改动过的字段**（`PATCH /api/v1/governance/models/{ref}`；`capabilities` 也只发变动过的成员），没动过任何字段时保存按住，提供方与模型标识在编辑态锁死，差量里永不出现 `endpoint` 与 `apiKeySecretRef`；弹层标题跟着变成「编辑模型」。启停开关与编辑表单共用 `governance.model.enable` 这一个动作。
- **UM-SET-005a**【调整】模型这一步同时打开它依赖的两件事——登记提供方（UM-SET-006）与登记模型——因为模型必须挂在已存在的提供方之下，只给一个入口等于让操作者用一次 422 自己发现顺序；两个入口的可用性分别来自 `governance.provider.register` 与 `governance.model.register`。模型登记与启停在移动端可用（表单以清单式呈现），并说明"没有可用模型 → 阶段运行会失败"。无查看权限的分组显示"无权查看"，不显示为 0 条。
- **UM-SET-006**【新增】（S5IF-GOV07、UM-ADM-002、UM-ADM-004）模型提供方登记内嵌**厂商目录**：选项来自 `GET /api/v1/governance/provider-catalogue`，界面不写死厂商名；每条给出显示名、接口地址、线协议、常用模型名与建议的凭证引用名，地址与模型名都可改成自由输入（私有网关、微调与改名的部署是常态）。目录只列 OpenAI 兼容协议的厂商，选中项带出固定线协议 `openai_compat`——本版本 `provider_for()` 不看 `adapter` 字段，所以它是显示为常量而不是选项，给下拉框等于给一个存进去必失败的地址。目录条目不代表已验证连通（AI-CAT-001）。编辑已登记的提供方时名称锁死，保存走 `PATCH /api/v1/governance/providers/{name}` 且只发改动过的字段（`providerClass`、`endpoint`、`apiKeySecretRef`、`enabled`、`vendor`、`suggestedModels`）；清空密钥引用输入框不发请求（PATCH 没有删除语义，空值会变成 422），`adapter` 永不 PATCH。

### 6.1 点击预算

以下预算从“打开对应入口”开始计数（从消息或待办进入计为第 1 次点击），滑动确认计为 1 次操作。实现必须不超过预算，并以端到端测试校验。

| 任务 | 路径 | 预算 |
| --- | --- | --- |
| 审批一个无警告的审批节点 | 待办卡片“去审批” → 底部面板“确认批准” | 2 |
| 审批一个含警告的审批节点 | 待办卡片 → “全部接受” → “确认全部接受” → “确认批准” | 4 |
| 回答一个问题（单题阶段，选建议） | 待办卡片 → 点建议 → “提交全部回答” | 3 |
| 回答 n 题的一页问卷 | 待办卡片 → 逐题选择／填写（n 次） → “提交全部回答” | n + 2 |
| 运行当前阶段 | 项目首页时间线中的主按钮 | 1 |
| 正式提交到某环境 | 部署任务卡片 → 滑动确认 | 2 |
| 上传一份需求材料 | 需求页“上传” → 选文件（分级已预选、自动解析） | 2 |
| 从通知查看一次失败的原因 | 点通知 → 失败原因即在首屏 | 1 |
| 新建项目（使用默认值） | 新建 → 下一步 → 下一步 → 创建 | 4 |

### 6.2 确认方式分级

| 风险 | 操作 | 确认方式 |
| --- | --- | --- |
| 无副作用或可撤销 | 刷新、筛选、标为已读、稍后处理、保存本地草稿 | 直接执行 |
| 影响流程、发出后不可撤销 | 提交整页问卷（模型据此重新生成） | 页面内一次提交；提交前逐题校验阻断题，按钮按住并说明还差几题，不额外弹确认 |

- **UM-IF-003**【调整】（UI-IF-003）本文交互以 S1 **现有**接口实现：整页问卷用 `POST /api/v1/questions/answers`（`AnswerQuestionsBody.answers[]` → `QuestionnaireAnswerView`），阶段问题列表用 `GET /api/v1/workflows/{workflowId}/questions`；需求条目读写用 `GET /api/v1/projects/{id}/blueprint/entries`、`GET /api/v1/projects/{id}/blueprint/section-schemas/{section}`（`section=requirements`）与 `POST /api/v1/stages/{stageId}/patches`；提供方测试连接用 `POST /api/v1/governance/providers/{name}/test-connection`（`ProviderHealthView.healthy/detail`），模型编辑用 `PATCH /api/v1/governance/models/{ref}`；取消单个 Agent 运行用 `POST /api/v1/workflows/{workflowId}/agent-runs/{runId}/cancel`，取消部署运行用 `POST /api/v1/deployment-runs/{runId}/cancel`；产物下载用 `GET /api/v1/artifacts/{id}/content?download=true`；单点登录用 `GET /api/v1/auth/oidc/request` 与 `POST /api/v1/auth/oidc/exchange`；装机事实用 `GET /api/v1/setup`。待办中心由跨项目审批节点列表、跨项目问题列表与项目阶段列表组合；轮询降级复用各资源的查询接口。

## 13. 数据需求

S5-M 不持久化业务数据。浏览器本地只保存：操作人姓名、语言、字号、深色模式、最近访问对象、各列表的筛选条件、本地“稍后处理”标记、人工编写的本地草稿（提交后清除）、每个项目上次使用的数据分级。整页问卷的作答草稿只在组件内存里，提交或离开页面即丢弃，不写本地存储；需求条目页也不保存本地草稿——那一页的权威副本是蓝图草稿。【新增】理由：UM-P-05、UM-MAN-002 与 UM-Q-003。
