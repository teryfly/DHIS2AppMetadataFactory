### 0.1 文档定位

本文档是全部子系统共享的非代码知识：架构决策、子系统划分、数据归属、依赖规则、库 API 集成约定、全局工作流结构、跨子系统调用目录、里程碑分工。各子系统的代码接口（Python 公共 API、REST API）由提供方在自己的仓库中定义与发布。

### 0.2 权威顺序

冲突时按以下顺序判定：

1. 目标 DHIS2 实例的 Capability Profile；
2. 对应版本 DHIS2 官方 API / Schema 文档；
3. 项目已批准的 App Blueprint 版本；
4. 总体 SRS；
5. 本文档；
6. 各子系统 SRS。

总体 SRS、本文档与各子系统 SRS 相互一致：总体 SRS 定义系统级需求，本文档定义子系统划分与集成约定，子系统 SRS 对前两者进行分解与细化。

## 3. 全局工作流结构

### 3.1 结构总览

```text
设计主线（每个项目一条，环境无关）
 [1] REQUIREMENTS      ── REQUIREMENT_GATE
 [2] DOMAIN            ── DOMAIN_GATE
 [3] DISCOVERY         （针对设计基准环境）
 [4] MAPPING           ── ARCHITECTURE_GATE
 [5] PAGE_DESIGN       ── DESIGN_GATE（模式 B；模式 A 为 SKIPPED）
 [6] BASELINE_COMPILE  （环境无关编译与校验）

Deployment Run（每个目标环境一个；按项目登记的晋级顺序）
 [R1] BIND_COMPILE      （目标环境发现 + 环境绑定编译）
 [R2] STATIC_VALIDATION ── PACKAGE_GATE
 [R3] DHIS2_VALIDATE    （执行计划、漂移检查、Snapshot、VALIDATE）
 [R4] COMMIT            ── DEPLOY_GATE（在 COMMIT 之前）
 [R5] POST_VERIFY
 [R6] FIXTURE_IMPORT    （可选；禁止 PRODUCTION）

交付
 [7] HANDOFF           ── HANDOFF_GATE（模式 B；至少一个非生产 Run 已 VERIFIED）
```

### 3.2 阶段与执行子系统

| 阶段 | 编排者 | 执行者（被调用的库） | 主要输出产物 | Gate |
| --- | --- | --- | --- | --- |
| REQUIREMENTS | S1 | S3（解析、Requirements Agent）；人工编写经 S2 | NRR（Blueprint 草稿中）、AGENT_OUTPUT | REQUIREMENT_GATE |
| DOMAIN | S1 | S3（Domain Agent）；人工编写经 S2 | 领域模型草稿 | DOMAIN_GATE |
| DISCOVERY | S1 | S4 | CAPABILITY_PROFILE、DISCOVERY_RESULT | 无 |
| MAPPING | S1 | S3（Mapping、Metadata Design、Fixture Agent〔模式 A〕）；S2（Registry、UID） | 映射、Registry、决策草稿 | ARCHITECTURE_GATE |
| PAGE_DESIGN | S1 | S3（API、UI、Fixture Agent）；S2 | 页面、API Intent、UI Intent 草稿 | DESIGN_GATE |
| BASELINE_COMPILE | S1 | S2 | OPENAPI、UI_SPECIFICATION、元数据基线、VALIDATION_REPORT | 无 |
| BIND_COMPILE | S1 | S4（该环境发现与探测）→ S2（环境绑定编译） | METADATA_PACKAGE、FIXTURE_PACKAGE、DIFF_REPORT | 无 |
| STATIC_VALIDATION | S1 | S2 | VALIDATION_REPORT | PACKAGE_GATE |
| DHIS2_VALIDATE | S1 | S4 | EXECUTION_PLAN、SNAPSHOT、DHIS2_IMPORT_REPORT | 无 |
| COMMIT | S1 | S4 | EXECUTION_REPORT、DHIS2_IMPORT_REPORT | DEPLOY_GATE（前置） |
| POST_VERIFY | S1 | S4 | POST_VERIFICATION_REPORT | 无 |
| FIXTURE_IMPORT | S1 | S4 | EXECUTION_REPORT | 随 DEPLOY_GATE |
| HANDOFF | S1 | S2 | FRONTEND_PACKAGE、HANDOFF_CHECK_REPORT | HANDOFF_GATE |

### 3.3 规则摘要

- 设计 Gate 批准后，S1 调用 S2 把该阶段工作草稿提升为正式 Blueprint 版本；Blueprint 正式版本只在 S1 调用时产生（草稿提升、交付模式升级、项目导入），因此 S1 总能同步获知版本变化并执行失效传播。
- 新版本产生后，受影响阶段 INVALIDATED；已完成的 Run 标记 OUTDATED（历史不可变）；进行中的 Run 取消（正在 COMMIT 的除外，完成后标记 OUTDATED）。
- 设计基准环境用于 DISCOVERY 阶段；每个 Run 在 BIND_COMPILE 中对其目标环境重新发现。
- 向 PRODUCTION 类环境的 Run，要求同一 Blueprint 版本已在至少一个非生产环境 Run 中 VERIFIED（M4 起可由平台管理员豁免）。

## 4. 数据归属

### 4.1 Schema 划分

| Schema | 所有者 | 内容 |
| --- | --- | --- |
| `core` | S0 | 产物元数据与类型目录、审计事件、幂等记录 |
| `cp` | S1 | 项目、目标环境登记、工作流、阶段、Deployment Run、Question（含 `answer_mode`）、Gate、审批、Change Request、事件流、通知、系统设置、用户/角色/会话/项目成员、受限产物授权、生产豁免、加密凭证、输入解析运行 |
| `bp` | S2 | Blueprint 版本索引、工作草稿、Patch、Registry（含环境绑定）、决策、依赖图索引、构建记录索引、导入导出账本 |
| `ai` | S3 | 输入解析记录、Agent 运行、Prompt、Model、提供方、数据策略、脱敏映射、用量与预算、评测结果、LLM 调用交换、阶段对话 |
| `dx` | S4 | Environment（含保护设置）、版本 Profile 索引、Capability Profile 索引、Discovery 索引、Snapshot 索引、Execution、环境锁、执行核对与维护记录 |

对象存储中的产物内容按 S0 的路径约定统一存放，只有 S0 读写。

### 4.2 归属规则

- 只有所有者子系统的代码可以读写自己 schema 中的表；其他子系统只能调用所有者的公共 API。
- 禁止跨 schema 外键、跨 schema 联表查询、跨 schema 视图。
- 跨子系统引用只保存 ID；Gate 绑定、构建记录、Registry 观测基准同时保存内容哈希。
- Registry 环境绑定中的 `observedHash` 与 Discovery 结果中的对象哈希不是冗余：前者是经批准的映射基准，后者是一次观测。
- 禁止把他方数据持久化（写入本方 schema、对象存储或任何跨进程缓存）作为事实来源；子系统为调用方完成一次操作而记录的执行结果（例如 S1 记录的某次漂移检查结论、步骤返回的产物 ID 与计数）属于本方记录，不算冗余。
- 允许对他方数据做**进程内短时缓存**，有效期不超过 60 秒，且只能用于展示类读取（列表、摘要中的显示字段）；**禁止**用于 Gate 判定、执行判定、`allowed-actions` 中与环境保护相关的判定，以及任何写入决策——这些场景必须实时调用所有者的公共 API。

## 6. 集成约定

### 6.1 公共 API 形式

- S0～S4 以 Python 包发布到私有 PyPI；S1 从私有 PyPI 按固定版本拉取依赖组装运行时。
- 每个库子系统在包内提供唯一公共入口模块 `<包名>.api`；其他子系统只能导入该模块及其导出的类型。
- 公共函数的参数与返回值使用 Pydantic v2 模型，全部带类型注解，并通过 mypy 严格模式检查。
- 公共 API 以语义化版本管理：不兼容变更提升主版本号，旧主版本至少保留一个里程碑。
- 每个库子系统必须同时提供其公共 API 的测试替身（Fake 实现，位于 `<包名>.testing`），使调用方可在不安装真实实现依赖（数据库之外的外部系统）的情况下开发与测试。

### 6.2 事务约定

- S0 提供工作单元（Unit of Work）：同一调用链上的多个子系统操作可加入同一数据库事务，由最外层调用方提交或回滚。
- 涉及外部 I/O 的公共函数（调用 LLM、调用 DHIS2、上传大文件到对象存储）禁止在调用方已开启的事务中执行；这类函数必须以 S0 提供的标记声明，并在内部自行管理短事务。在事务中调用此类函数必须立即报错。
- 状态变更与其审计记录必须在同一事务中提交。

### 6.3 长任务、进度与取消

- S3 的 Agent 运行、S4 的发现与执行是长任务，以同步库函数形式提供，由 S1 在 Temporal 活动中调用。
- 长任务函数必须接受 S0 定义的 `ProgressReporter` 与 `CancellationToken` 参数，定期回报进度并响应取消（不可中断的步骤除外，如已提交的 DHIS2 导入）。
- 长任务必须把可恢复的中间状态持久化在自身 schema 中（如 DHIS2 异步任务 ID），以支持活动重试时继续而不是重做。

### 6.4 幂等

- 会产生副作用的公共函数必须接受幂等键；同键重复调用返回首次结果。幂等记录使用 S0 幂等存储。

### 6.5 错误

- 全部公共函数以 S0 定义的 `FactoryError` 层次抛出错误，包含错误码、是否可重试、来源阶段、关联产物与详情；错误码目录由 S0 维护，子系统可登记自己的错误码。
- S1 负责把错误映射为公共 REST 错误响应。
- 每个错误码只有一个所有者（FD-COM-001a）：所有者是定义该条件的一方，其他子系统可以抛出该码，但不得把它登记到自己名下。一个子系统可登记的码集合必须在提供方登记之后计算，不得取决于进程内的导入顺序——同一份代码在只装替身与装有真实提供方时登记出不同的码集，会让严格目录在一种顺序下报 `RegistryConflictError`。

### 6.6 产物读写

- 全部产物经 S0 产物存储创建与读取；创建方必须声明类型、数据分级、来源产物（如有）与构建记录（如有）。
- 产物内容不可变；修改即新产物。每个产物类型登记其所有者子系统，只有所有者可以创建该类型。

### 6.7 标识、时间与格式

- 内部 ID：带类型前缀的 ULID。
- 时间：ISO 8601 UTC；需要确定性的代码（Compiler）只能从调用参数中的构建上下文获取时间，不得读取系统时钟。
- 哈希：`sha256:<hex>`。对数据结构求哈希使用 S0 规范化形式（键排序、紧凑、UTF-8）；JSON 文件使用 S0 文件形式（键排序、2 空格缩进、LF）；产物内容哈希为文件字节哈希（S0 FD-COM-003）。
- Blueprint 版本号：`MAJOR.MINOR.PATCH`，由 S2 分配。
- DHIS2 对象 UID：由目标 DHIS2 实例官方 UID 生成接口产生，经 S4 获取、由 S2 入池与分配。

### 6.8 可观测性

- 统一使用 S0 的日志与追踪工具：结构化 JSON 日志含 `correlationId`、`operator`、`projectId`、`workflowId`、`stageId`、`agentRunId`、`artifactId`、`executionId`（适用时）；OpenTelemetry 追踪覆盖 API、工作流活动、模型调用、DHIS2 调用。

### 6.9 安全

- DHIS2 凭证只由 S4 通过 S0 Secret 适配器解析；模型 API 密钥只由 S3 解析；通知渠道密钥只由 S1 解析。
- 凭证禁止出现在产物、日志、审计、异常信息、SSE 事件与错误 `details` 中；界面只能经 `PUT /api/v1/secrets/{name}` 单向写入，之后只回引用，不回显值、掩码、长度或前缀。
- 身份由 `FACTORY_AUTH_MODE` 决定：`off` 兼容模式下 `X-Operator` 即身份、不设访问保护（仅供本地演示与评估）；`local|oidc|both` 下所有业务请求需会话认证，改变状态的请求需 CSRF 令牌，停用账号立即失效。生产部署必须启用认证，并通过 HTTPS 提供服务。
- 认证与权限的原语（角色、项目成员、受限产物授权、生产豁免、多人审批与职责分离）由 S1 持有；S5/S5-M 只消费 `allowed-actions` 与 `auth/session`，不自行推断权限。

### 6.10 校验问题（Issue）统一结构

- 系统内所有“校验问题”（静态校验、跨产物校验、DHIS2 ImportReport 标准化后的问题、Agent 输出中的问题）使用同一结构，唯一定义方为 S2（BP-VAL-001）：问题 ID、规则 ID、级别 `level`（`BLOCKING` / `WARNING` / `INFO`）、消息、businessKey、UID、DHIS2 类型、产物 ID、位置、分节、来源阶段、建议处理、详情。
- S4 的 ImportReport 标准化问题（DX-EXE-027）与 S3 输出中的问题必须遵循该结构；级别字段一律称为 `level`，不得使用 `severity` 等别名。Question 的严重程度（`HIGH` / `MEDIUM` / `LOW`）是另一概念，不受本条影响。

### 6.11 公共 REST 线上约定

以下约定适用于 S1 暴露的全部公共 REST 端点（含转发端点），由 S1 负责落实，S5 依赖其生成客户端：

| 主题 | 约定 |
| --- | --- |
| 契约描述 | OpenAPI 3.1；每个操作的请求体与 2xx 响应体都必须是具名组件（禁止自由对象）；转发端点的请求由 S1 定义请求模型并校验后再转给提供方 |
| 字段命名 | 字段名一律 camelCase；枚举值一律 UPPER_SNAKE；转发提供方的 snake_case 模型时由 S1 投影为 camelCase；同一响应内禁止混用两种写法。例外：系统设置的**键**属于数据而非字段名，可保持 snake_case，但必须在 OpenAPI 中声明为枚举 |
| 分页信封 | `{items, limit, total?, offset?, nextCursor?}`；普通列表用 `offset`；审计、产物、事件类列表用 `nextCursor`（游标）；`total` 代价过高时省略，不得填 0；排序参数统一为 `sortBy` + `sortDir` |
| 跨切请求头 | `X-Operator`（`auth=off` 时改变状态的请求必填；认证模式下操作者取自会话）、`Idempotency-Key`（创建类与执行类）、`Accept-Language`（`zh-CN` / `en`）、`X-Correlation-Id`（入站沿用、出站回显）、`traceparent`；认证模式下另有会话 Cookie 与 `X-CSRF-Token`；响应头包括幂等重放标识、`X-Correlation-Id`、产物内容的 `X-Data-Classification`。全部必须在 OpenAPI 中声明，响应头名称以 S1 实现为准统一后声明 |
| 幂等 | `Idempotency-Key` 只从请求头读取，请求体中不设幂等键字段 |
| 长任务受理 | 启动长任务的端点统一返回 202 与受理信封（含可观察的标识），不返回同步结果，不暴露执行引擎等部署细节；结果经 SSE 与查询端点观察 |
| 批量回答 | 同一阶段的多道 Question 由 `POST /api/v1/questions/answers` 一次提交：先在一个事务内记录全部答案，再最多恢复一次 Agent 运行；响应带回恢复后仍开放的问题，供界面就地渲染下一轮（CP-Q-005） |
| 外部探测 | 环境连接测试与模型提供方连通性探测是**会产生外部访问的 POST**：它们返回探测结论（可连通/不可连通及原因），而不是把“连不通”当作 5xx；探测不生成内容、不计费、不回显凭证值或引用（S5IF-GOV20） |
| 模型编辑 | 已登记的提供方与模型用差量 `PATCH` 编辑：只写被点名的列、空补丁 422、未知字段 422、审计记 `before`/`after`；禁止用 `POST` upsert 代替编辑（S5IF-GOV06） |
| 错误码 | S1 维护公共错误码目录。与 S1 目录中某码语义相同的提供方码一律归一为 S1 的码；有独立含义且已在 S0 目录登记的提供方码允许透出；未登记且与 S1 码语义重叠的提供方码不得透出；按码定义 `details` 结构 |
| 凭证 | 业务请求只接受 Secret 引用（`env://…`、`db://…`），**但引用可以整体省略**：一个不需要鉴权的地址（本机 Ollama / LM Studio / llama.cpp）就让它为空，服务端因此不发 `Authorization` 头（契约 1.19.0）。省略不等于编造——填进去一个不存在的引用是登记通过、解析必失败。唯一的值接收端点是 `PUT /api/v1/secrets/{name}`，它单向接收值本身（S5IF-SEC01），并且不声明 `Idempotency-Key`（该路径不进回放表，可重复性来自 `PUT`）。响应、SSE、错误 `details`、审计前后摘要中禁止出现凭证的值、掩码、长度、前缀，也禁止出现任何**由密钥派生**的检查值 |
| 版本与追溯 | 契约按语义化版本管理，破坏性变更提升主版本并记录于 CHANGELOG；当前契约为 **1.19.0 / 147 条路径 / 172 个操作**；每个操作带 `x-requirements` 扩展字段，列出其实现的需求编号；`servers` 留空，由部署侧注入（S5 与 S1 同域部署） |

### 6.12 构建、迁移与部署

- 每个库子系统在自身仓库维护其 schema 的 Alembic 迁移（独立版本表）；S0 提供迁移运行器，按 `core → dx → bp → ai → cp` 顺序执行。
- 每个库子系统在其 `api` 模块中导出 `initialize()`（登记本子系统的产物类型、审计事件类型、错误码与 ID 前缀）和 `MIGRATION_CONFIG`（本 schema 的迁移配置）；S0 另导出 `initialize_foundation()`。
- 后端进程启动顺序：日志与追踪初始化 → 迁移（仅 factory-api，按 `core → dx → bp → ai → cp`）→ S0 `initialize_foundation()` → S4、S2、S3 的 `initialize()` → S1 自身登记。
- factory-api 多实例之间的 SSE 扇出使用 PostgreSQL LISTEN/NOTIFY，不引入其他中间件。
- S1 仓库负责组装：以固定版本依赖 S0～S4，构建 `factory-api`（REST + SSE，无状态，可水平扩展）与 `factory-worker`（Temporal 工作进程，可水平扩展）两个镜像，并提供 Docker Compose（开发与评估）与 Helm Chart（生产）。
- S5 独立构建静态前端镜像。
- 除镜像交付外，S1 仓库另提供一套面向单机的裸机部署脚本（`install.sh` 安装、`start.sh` 启停），用于评估与小规模落地：nginx 以 TLS 同时前置静态前端与 `/api/v1`（同域是硬要求，S1 不提供 CORS），对外端口可配置；`factory-api` 由 systemd 守护并只监听 `127.0.0.1`，`factory-worker` 由第二个 systemd 单元运行（必须在 api 通过 `/healthz` 后启动，迁移无并发锁）；`/readyz` 以真实数据库语句探活，`/healthz` 只表示进程存活；对象存储允许指向本地文件系统（`file://`）以免为此路径引入 S3 服务；数据库角色与建库由脚本幂等创建，schema 仍由启动时的迁移建立。该路径不改变任何接口约定，只是 FR-DEP-003 之外的又一种交付方式。
- 每个库子系统的 CI 必须使用 PostgreSQL 容器运行本子系统测试，并运行其依赖方提供的公共 API 兼容性测试。

## 8. 跨子系统关键流程

### 8.1 Agent 驱动的设计阶段

1. 用户在 S5 发起阶段运行 → S1 校验状态 → S1 在 Temporal 活动中调用 S3 启动 Agent 运行（携带阶段、项目、草稿引用、输入产物 ID、进度回调）。
2. S3 经 Policy Engine 判定 → 构造上下文（调用 S2 读取条目、经 S0 读取产物）→ 调用模型 → 校验输出 → 调用 S2 把 Patch 加入工作草稿。
3. S3 返回运行结果（完成 / 等待输入 / 失败 / 策略拒绝），其中包含 Question 列表（每题带 `answerMode`、建议与 `recommended` 标记）；S1 保存 Question，必要时置阶段 WAITING_INPUT。
4. 用户一次提交同一阶段的整页问卷（`POST /questions/answers`）后，S1 先在事务内记录全部答案，再调用 S3 恢复运行至多一次；恢复后仍开放的问题随响应返回，可直接渲染为下一轮问卷。
5. 运行完成 → S1 置阶段 WAITING_APPROVAL，创建 Gate 并绑定草稿哈希（从 S2 读取）。
6. Gate 批准 → S1 在同一事务中调用 S2 提升草稿为版本、置阶段 PASSED、执行失效传播、写审计。

### 8.2 Deployment Run 提交

1. S1 创建 Run → 调用 S4 探测与发现目标环境 → 调用 S2 环境绑定编译 → 调用 S2 静态校验 → 创建 PACKAGE_GATE。
2. 批准后 S1 调用 S4 生成执行计划、漂移检查、Snapshot、VALIDATE → 创建 DEPLOY_GATE。
3. 审批时与 COMMIT 请求时，S1 再次调用 S4 漂移检查与环境保护查询。
4. 用户请求 COMMIT → S1 复核 Gate → 调用 S4 COMMIT（带幂等键）→ S4 获取环境锁、提交、持久化异步任务 ID、轮询至完成 → 返回结果 → S1 调用 S4 部署后验证 → 可选 Fixture 导入。

### 8.3 Change Request

1. 用户创建 CR → S1 调用 S2 影响分析，并补充已部署环境 → 形成影响报告 → 批准。
2. 执行时 S1 从受影响的最早阶段重开主线，其余阶段保持原状态。

## 11. 术语补充

总体 SRS 附录 A 的术语全部沿用，新增：

| 术语 | 定义 |
| --- | --- |
| 设计主线 | 与环境无关的阶段序列 REQUIREMENTS 至 BASELINE_COMPILE |
| Deployment Run | 把一个 Blueprint 版本部署到一个目标环境的完整过程，含 R1～R6 |
| 设计基准环境 | 项目目标环境中用于 DISCOVERY 阶段的环境 |
| 工作草稿 | 设计阶段内叠加了 PROPOSED Patch、尚未批准的 Blueprint 状态 |
| 基线编译 / 环境绑定编译 | 环境无关的编译 / 以目标环境发现结果与能力解析引用后的编译 |
| OUTDATED | 已完成 Run 所基于的 Blueprint 版本已不是当前版本 |
| 操作者（Operator） | MVP 中由请求头 `X-Operator` 声明的操作人名称；M4 起由认证身份取代 |
| 公共 API（库） | 子系统包中 `api` 模块导出的函数与类型，是跨子系统调用的唯一入口 |
| 工作单元 | S0 提供的跨子系统共享数据库事务上下文 |
